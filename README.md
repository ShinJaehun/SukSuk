## 쑥쑥수학의 목표

쑥쑥수학은 초등학생이 곱셈과 나눗셈을 실제 공책에 풀이하듯이 한 단계씩 따라가며 연습하도록 만든 앱입니다. 일반적인 계산 앱은 최종 답만 입력하고 정답 여부를 확인하는 경우가 많습니다. 하지만 초등 수학에서 중요한 것은 최종 답뿐만 아니라 다음과 같은 계산 과정입니다.

- 어떤 자리부터 계산해야 하는가
- 받아 올림을 어디에 적고 어떻게 활용해야 하는가
- 나눗셈에서 몫을 어디에 세워야 하는가
- 곱한 값을 어디에 쓰고 어떻게 빼야 하는가
- 받아 내림과 끌어 내림을 어떤 순서로 처리해야 하는가
- 마지막 나머지를 어떻게 확인해야 하는가

쑥쑥수학은 이런 계산 과정을 학생이 직접 입력하면서 연습할 수 있도록 설계되었습니다.

## 리팩토링한 이유

예전 버전의 쑥쑥수학은 Java, XML Layout, Activity, Fragment 중심으로 만들어졌습니다. 당시에는 자연스러운 Android 개발 방식이었지만, 시간이 지나면서 유지보수와 확장 측면에서 몇 가지 한계가 생겼습니다.

### 기존 구조의 어려움

- 계산 단계별 로직이 화면 코드와 강하게 결합되어 있었습니다.
- 곱셈, 나눗셈, 문제 유형별 코드가 여러 Fragment에 흩어져 있었습니다.
- 현재 풀이 단계, 입력값, 정오답 판정, 화면 표시가 한 클래스 안에 섞이는 경우가 많았습니다.
- 화면 회전, 앱 일시 중지, 복귀 상황에서 진행 중인 문제 상태를 안정적으로 유지하기 어려웠습니다.
- 새로운 문제 유형을 추가하거나 기존 계산 과정을 수정할 때 영향 범위를 파악하기 어려웠습니다.
- 최신 Android 개발 환경과 거리가 멀어 장기적인 유지보수가 어려웠습니다.

그래서 리팩토링 버전에서는 기능을 무리하게 늘리기보다, 먼저 기존 앱의 핵심 가치인 **단계별 계산 연습**을 더 안정적으로 유지하고 확장할 수 있는 구조를 만드는 데 초점을 두었습니다.

## 리팩토링 방향

### 1. Java/XML/Fragment 중심 구조에서 Kotlin + Jetpack Compose 구조로 전환

기존 버전은 여러 Activity와 Fragment를 조합하여 화면을 구성했습니다.

리팩토링 버전에서는 Kotlin과 Jetpack Compose를 사용해 화면을 선언적으로 구성합니다. 화면을 직접 찾아서 수정하기보다, 현재 상태를 기준으로 UI가 다시 그려지도록 만들었습니다.

이를 통해 화면 코드가 더 단순해지고, 상태 변화에 따른 UI 표현을 관리하기 쉬워졌습니다.

### 2. 화면 코드와 계산 로직 분리

예전 버전에서는 문제 풀이 단계, 입력값 확인, 정답 처리, 화면 표시가 같은 코드 안에 섞여 있는 부분이 많았습니다.

리팩토링 버전에서는 계산 진행 상태를 Domain 영역으로 분리하고, 각 단계의 정답 여부는 Evaluator가 판정하도록 정리했습니다.

대략적인 흐름은 다음과 같습니다.

```text
Problem
  → Pattern 감지
  → PhaseSequence 생성
  → DomainState 생성
  → ViewModel에서 입력 처리
  → Evaluator가 정답 여부 판정
  → UiState로 변환
  → Compose 화면에 표시
```

이 구조 덕분에 다음 요소를 화면 코드와 분리해서 다룰 수 있습니다.

- 지금 어떤 계산 단계인가
- 어떤 칸이 입력 가능한가
- 어떤 칸을 강조해야 하는가
- 사용자 입력이 맞는가
- 정답일 때 다음 단계는 어디인가
- 오답일 때 어떤 피드백을 줄 것인가

### 3. 문제 유형을 Pattern으로 정리

리팩토링 버전에서는 문제 유형을 문자열이 아니라 명확한 Pattern으로 다룹니다.

#### 나눗셈 Pattern

- `TwoByOne` : 두 자리 수 ÷ 한 자리 수
- `TwoByTwo` : 두 자리 수 ÷ 두 자리 수
- `ThreeByTwo` : 세 자리 수 ÷ 두 자리 수

#### 곱셈 Pattern

- `TwoByTwo` : 두 자리 수 × 두 자리 수
- `ThreeByTwo` : 세 자리 수 × 두 자리 수

문제를 Pattern으로 정리하면 문제 유형별 계산 단계를 더 명확하게 정의할 수 있고, 이후 새로운 유형을 추가할 때도 구조를 유지하기 쉽습니다.

### 4. 계산 과정을 Phase로 분리

쑥쑥수학에서 중요한 것은 최종 답이 아니라 계산 과정입니다. 그래서 리팩토링 버전에서는 계산 과정을 여러 Phase로 나누어 관리합니다.

#### 곱셈 Phase 예시

- 첫 번째 부분곱 입력
- 다음 계산 준비
- 두 번째 부분곱 입력
- 합산 입력
- 완료

#### 나눗셈 Phase 예시

- 몫 입력
- 중간 곱셈 입력
- 받아 내림 입력
- 끌어 내림 입력
- 뺄셈 입력
- 다음 계산 준비
- 완료

이렇게 계산 단계를 Phase로 나누면 “학생이 지금 어떤 수학적 행동을 하고 있는지”를 코드에서도 명확하게 표현할 수 있습니다.

### 5. ViewModel 중심의 상태 관리

리팩토링 버전에서는 곱셈과 나눗셈 화면에 각각 ViewModel을 두고, 현재 문제 상태와 입력 상태를 관리합니다.

ViewModel은 다음 역할을 담당합니다.

- 새 문제 시작
- 숫자 입력 처리
- 입력 확정 처리
- 입력 지우기
- 정답/오답 판정 요청
- 다음 단계 이동
- 현재 상태를 UI 상태로 변환
- 진행 중인 문제 상태 저장 및 복원

이를 통해 Compose 화면은 “무엇을 보여줄지”에 집중하고, 계산 진행 로직은 ViewModel과 Domain 영역에서 처리하도록 분리했습니다.

### 6. 진행 중인 문제 상태 복원

곱셈과 나눗셈 문제는 한 번의 입력으로 끝나지 않고 여러 단계를 거쳐 진행됩니다. 따라서 앱이 잠시 중단되거나 화면이 다시 구성될 때 학생이 풀고 있던 단계가 갑자기 초기화되면 학습 흐름이 끊깁니다.

리팩토링 버전에서는 현재 문제, 진행 단계, 이미 확정된 입력값, 현재 입력 중인 값을 저장하고 복원할 수 있도록 정리했습니다.

특히 복원할 때는 단순히 화면 상태를 억지로 되살리는 것이 아니라, 저장된 입력 이력을 다시 적용하여 Domain State를 재구성하는 방식을 사용합니다.

이 방식은 다음과 같은 장점이 있습니다.

- 중간 상태를 더 안전하게 복원할 수 있습니다.
- 계산 로직의 일관성을 유지할 수 있습니다.
- 문제와 입력 이력만 있으면 현재 단계를 다시 만들어낼 수 있습니다.

### 7. 문제 공급 구조 분리

리팩토링 버전에서는 문제를 화면에서 직접 생성하지 않고, 문제 공급 구조를 분리했습니다.

이를 통해 같은 화면 구조 안에서 다음과 같은 모드를 다루기 쉬워졌습니다.

- 선택한 유형만 반복 연습
- 여러 유형을 섞은 챌린지 모드
- 특정 문제를 고정해서 확인하는 디버그 모드
- 이후 학습 기록, 통계, 추천 기능과의 연결

### 8. Hilt 기반 의존성 주입

리팩토링 버전에서는 Hilt를 사용해 ViewModel, Domain Factory, Evaluator, 문제 생성 관련 객체를 주입받도록 구성했습니다.

각 객체가 필요한 의존성을 직접 생성하지 않고 외부에서 전달받도록 하여, 코드 구조를 더 명확하게 만들고 테스트 가능한 구조로 발전시킬 수 있게 했습니다.

## 현재 구현된 화면 흐름

앱은 메인 화면에서 시작합니다.

사용자가 `문제풀기`를 선택하면 문제 유형을 고를 수 있고, 선택한 유형에 따라 곱셈 또는 나눗셈 연습 화면으로 이동합니다.

각 연습 화면에서는 학생이 계산 과정의 각 칸을 순서대로 입력합니다.

- 정답이면 다음 단계로 이동합니다.
- 오답이면 피드백을 주고 다시 입력하도록 합니다.
- 한 문제를 끝까지 풀면 완료 피드백을 제공합니다.
- 챌린지 모드에서는 여러 유형의 문제를 섞어서 풀 수 있습니다.
